# Hard-delete transactions; track history in a separate append-only audit log, not soft-delete

Deleting a `Transaction` removes the row from the database entirely — there is no `deletedAt` column, and the Transaction table always reflects exactly the currently-correct set of trades. Traceability instead comes from `TransactionAuditLog`: every create, edit, and delete writes an entry there (action type plus a full before/after snapshot), and that table is never updated or deleted from application code.

Soft-delete was the more obvious default and was considered — it's the common pattern for "let me undo this." It was rejected because it would have coupled two different concerns into one table: `Transaction` would need to carry both "what's true right now" (what `calculatePnl` reads) and "what happened over time" (what the user reviews), forcing every query against it to filter out soft-deleted rows and every read of "current state" to reason about that filter. Splitting them means `Transaction` stays exactly what `calculatePnl` already assumed it was — the live, current set of trades — and the audit log is purely additive, with no read path anywhere needing to know it exists.

The real cost of this choice: there is no "undo" button. A delete is permanent from the Transaction table's point of view; recovering a deleted row means manually reading its `before` snapshot off the corresponding audit log entry and re-entering it as a new transaction. This was accepted explicitly — restoring exact undo was out of scope for this feature (see the spec's Out of Scope section) — but a future reader adding a "restore" feature should know this is why one doesn't already exist.
